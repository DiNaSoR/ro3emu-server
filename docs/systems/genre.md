# Build presets (MG_Genre)

The server persists the client's `DBGenre` as message 5008. Its five Build presets map the `PBChildSystemType` numbers to the selected child plan IDs: skill 1, attributes 2, equipment 3, cards 4, totems 5, Soul Echoes 6, pets 7, and seasonal talent 8. The source contracts are `MG_Genre.proto`, `MG_DB.proto`, `LC_SchemeServerHelper.lua` and `LC_DAL_Scheme.lua`. `PublicParamConfig.SchemeNum=5` and `SchemeNameNumMax=8` supply the count and name length. A new role starts with five presets referencing the child's current plans, then saves 5008. The client labels generic scheme index 0 as preset 1; using indices 0-4 is inferred from that convention and the Build UI calls.

`82806` updates a preset's child map and, when `isApply=true`, stages every selected owner before persisting. Statistics and skill plans are real independent five-slot data, rather than aliases for the active plan. Equipment and card selection move physical item instances; totems update active item markers; Echoes and pets validate owned selections; seasonal talent checks its own unlock/cooldown rules. A failed child validation leaves the role and all blobs unchanged. A successful apply writes the Build map, child blobs, role progress, and item changes in one SQLite transaction, then publishes all owner syncs and a property refresh. `82816` changes the preset's name; `82823` and `82825` project selected child states to answer property and power queries. The power reply sums the selected child plans' stored `PowerUnit`s, using the pet, totem, and Soul Echo scores currently calculated by their owners. `LC_SchemeHelper.lua:772-798` confirms the client's child `PowerUnit` lookup. The cross-system aggregation on the server is inferred; see the search note below.

The social messages `82800`-`82813`, `82824`, and `82828` store recommendation records in each participant's `DBGenre`. A responder can save and send a concrete plan only for owned resources, and only the named seeker can apply the committed reply. Share codes expire after one day (inferred policy). The apply wire sends a donor response ID, a Build preset ID, `systemType` mapping child type to recipient target child plan, and optional `childType` flags for partial replacement. `UI_Sys_GenreManualPanelModel.lua:970-1011,1550-1588` confirms those map meanings. Applying resolves donor equipment, totem, and Echo GUIDs to recipient-owned instances of the same item entry, requires recipient-owned card entries and pet IDs, revalidates each selected child, and commits the resulting preset and child state together. Equivalent same-entry item resolution and immediate selection of the resulting Build are inferred policies where the client request does not specify server behavior. A missing equivalent fails with a nonzero result; it never reports an applied build that the owner rejected.

## Power aggregation search

A search for `GenrePlanPower|GetPlanPower|CalculateGenrePower|SchemePower` across the exported `data/config`, `data/sceneeditor`, `data/nav` and `data/loc` files, both client Lua trees (`re/lua-src`, `re/clientB/lua-src`), the decompiled C# (`re/decomp`) and both proto trees (`src/Ro3Emu.Server/Protos`, `re/proto`) found only generated message names (`Network/NW_Helper_PBDefine.lua:9319`) and the message definition itself (`MG_Genre.proto:171`). This regex is a bounded search for those names, not proof that a differently named server formula does not exist. The original rating algorithm is unrecovered, and the client's sum for display is distinct from any server aggregation (see [equipment-rating-evidence.md](../research/equipment-rating-evidence.md) for the related item-score evidence). The preset sum here is therefore an explicitly inferred policy over the child scores this emulator actually stores.
