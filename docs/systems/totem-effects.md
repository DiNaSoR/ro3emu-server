# Effective totem skills and buff execution

`TotemService` selects deployed skill instances after superior-skill suppression and the `_iIsCoexist` rule. `TotemEffects.Attributes(session,item,skill)` evaluates each selected skill's `_kBasicAttribute` and all referenced `SpecialEffectConfig` tuples; `RefreshAsync` reconciles source-owned opcode-2 passive registrations and active floor buffs after plan, skill or item changes. The durable source is the totem instance in pack 4 and its selected plan, not a separate special-effect blob. TotemService and Genre plan switching call these methods.

## Exact input population and arithmetic

`data/config/TotemSkillConfig.json` has 97 `_kSpecialAttribute` references. All 97 resolve to `SpecialEffectConfig`: tuple counts are opcode 1 = 37, 2 = 38, 7 = 8, 9 = 18, 10 = 10, 12 = 5, 18 = 4. This was joined directly by ID, not by adjacent row numbers. `re/lua-src/Logic/SpecialEffect/LC_SpecialEffectHelper.lua` supports op1 raw attribute, op7 `floor(this item skill count/step)*value`, op9 `floor(BaseLv*coefficient/10000)`, and op10's exact HP comparators. The op10 evaluator obtains a stat sheet with only op10 suppressed during its nested `Stats()` call; no current totem op10 changes MaxHP. It uses current HP, inclusive `>=80%` and `<=50%` as encoded. The preview helper's localization says “above/below,” but its comparison operator is authoritative at the boundary. `AttributeConfig` composes components such as 1033/1043 rather than treating them as displayed 103/104.

The five current totem opcode-12 tuples are `[12,1,4002/4003/4004/4005,2,1,50,5-or-6,1]`. The adjacent opcode-1 tuple gives the destination attribute 213, 227, 229, 216 or 207. The effect descriptions say each active floor grants another 0.5%; raw 50 is one half percent in those four percentage attributes. The implementation counts only timed floor buffs with that category and this totem's source GUID. **This decoder is inferred**: the client preview searches an older `_kBuffCategory1` field while this export contains `_kBuffCategory`, and it does not execute operation 12. The four opcode-18 descriptions explicitly add one maximum floor to the current totem's category, so the source-specific stack cap is `BuffConfig._iMaxStack + 1` where active. The four 2530401-2530701 passive descriptions say a further raw 50 or 100 per active floor, paired with their opcode-1 base attributes 111/209/112/210; counting the floor category 4001 is also **inferred**.

The combat hook aggregates only selected Totem skill attributes and active buffs whose source GUID is one of those Totems. It applies 211/213 plus distance-specific 227/229 to outgoing damage, 216 to incoming damage, and 207 to healing at the AttributeConfig `/10000` scale. Raw 209/210 adjust the existing 150% critical multiplier; 103/104/105/106 and their components already flow through the ordinary ATK/MATK/DEF stat sheet and are not added a second time. `SkillConfig._iDistanceType=2` selects ranged physical damage; other physical skills use 227. These modifier order and rounding choices are **inferred** from attribute labels and the existing CombatService formula. The hook leaves non-Totem baseline damage unchanged. The focused test checks baseline, a selected-skill positive modifier, an active floor's extra modifier and removal on plan switch.

## Opcode-2 buff families

Every opcode-2 target resolves to a `BuffConfig` row. Its 38 tuples include repeated IDs (2515601 and 2509901) with separate source-skill modifiers. The rows are zero-time configurations, mostly marked `iPassiveBuff=1`; a few are modifier rows with `iPassiveBuff=0`. Normal `BuffService.AddAsync(...,duration=0)` would invent a 60-second buff. `BuffService.AddPassiveAsync` records `(source item GUID, buff ID)` indefinitely. The one referenced icon-enabled modifier (2530101) uses a zero-time 31104 entry; `_iShowIcon` controls whether the current server sends a passive registration in 31104. `RefreshAsync` removes exact stale registrations and derived timed stacks when a source leaves the active plan; `_iDeadClear` remains honored by `BuffService` and revive re-registers passives. Ordinary unrelated AddAsync behavior remains unchanged. `AddSourcedAsync` keeps independent timed procs from separate totems. The ordinary `AddAsync` refresh selects only non-Totem-owned buffs, so a coincident config ID can coexist and removing a Totem source leaves the ordinary buff intact. Active floor buffs use the same GUID on refresh, carry an actual pile count in 31104 and server state, and add their `_kChangeAttri` per floor to the stat pipeline. Their IDs and categories are:

The remaining zero-time passive families are 2503201/2513201/2514701/2505901 (on **player** kill -> timed 2503401/2513401/2514901/2506101), 2516501/2508301 (on damage **from a player** -> timed 2516701/2508501), 2504401/2514401 (healing a low-HP target), and 2530401-2530701 (stack-dependent attributes). Localization entry 10220300957 explicitly says “When taking damage from a player,” so the monster-hit callback must not trigger those recovery buffs. `OnPlayerKilledAsync` and `OnPlayerDamagedAsync` are entry points awaiting an authoritative PvP caller. In the current `CombatService.CastAsync`, `_iRelease=1` resolves `req.TargetId` only through `FindMonster` and rejects a missing monster. `EffectAsync` sends flat healing to the caster, then builds damage targets solely from `MonsterUnit`; `MonsterAttackAsync` is the only implemented monster-to-player hit path. Thus no current server hit path calls either PvP entry point, and the present heal path evaluates 2504401/2514401 only against the healed self. An ally-targeted cast would need a distinct validated player-target route before those buffs could be applied to an ally. This is a current-server routing limit, not a claim that the client lacks such a feature.

## Source and verification boundary

During role loading, totem reconciliation refreshes the server's property snapshot without sending a premature
31008/31048 update. Visible passive registrations are resent by the existing SceneService path after ENTITYSELF.
Live plan/skill changes still publish properties immediately. The unchanged equipment-stat regression verifies
that login initialization no longer leaves an earlier base-ATK packet ahead of the equipment update.
Removing a stale totem-owned buff during loading also remains silent; a two-role wire regression verifies
that switching roles on the same connection removes the old stack before the new ENTITYSELF without sending
an earlier 31008/31105 for that unit, and restores the new role's base ATK.

The authoritative static inputs inspected were `data/config/TotemSkillConfig.json`, `SpecialEffectConfig.json`, `BuffConfig.json`, `AttributeConfig.json`, `Localization_en.json`; `re/lua-src/Logic/Totem/LC_TotemHelper.lua` (deployed effective state, around lines 3460-3605); and `re/lua-src/Logic/Buff/LC_BuffConfigHelper.lua:537-632`. These prove IDs, categories, descriptions, stat types and client display logic, not recovered authoritative server timing. No unsupported missing-content claim is made here. `TotemEffectsTests` injects a deployed totem skill list, verifies inclusive HP condition, passive registration, cast-created floor with pile count, opcode-12 floor bonus, and exact source cleanup on plan switch. Behavior in the original client has not been verified.
