# Appearance lottery (NewActivity type 7)

`LC_LotteryServer.SendLotteryReq` sends `LOTTERY_REQ` (83410), with `poolId` and the one/ten/fifty draw enum. `MG_Lottery.proto` supplies the `LotteryResp` item list, `poolData`, and pity records. `LC_DAL_AppearanceLottery._processAppearanceLottery` reads `poolData.poolId` before other response fields, so every reply carries a populated `LotteryPoolData`, including refusals. The 5011 `DBLotteryDataIncrement` projects all configured `DrawConfig` banners with `isOpen`; the client full sync initializes its pool and pity asset maps even when pity is empty (`LC_DAL_AppearanceLottery.lua:450-525`). `LC_DAL_AppearanceLottery.OnDrawByType` uses `_kMinRoll`, `_kMidRoll`, `_kMaxRoll` as ticket ID plus draw count and offers `_kRollItem` currency purchase for missing tickets. Only owned-ticket draws settle here; missing tickets return `ItemsShort` without a currency charge.

Pool visibility follows `DrawConfig._iFunctionID` and, when `_iNewAct` is nonzero, the corresponding `NewActivityConfig` current playbook, open condition and `TimeLimitConfig` window. Banner 200 points to activity 1001, banner 201 to 1000; both type-7 activity rows use time limit 1018. These event rows are projected by NewActivity separately. Banner 201 uses item 1250717, one/ten/fifty modes, and groups 201/202. Banner 200 uses item 1250709, one/ten modes, and groups 1/2/3. Its `_kMaxCnt=[2,20]` is a lifetime cap. Other rows with `[1,1000]` reset their per-banner count on the realm-local civil day. Function 3302 is quest gated; function 3303 is level 42 gated in the current `FunctionConfig` and `LC_ConditionList`.

For each draw, the service samples an eligible `DrawPoolConfig` row by `_iWeight` and then samples one tuple uniformly from its `_kItem`. That tuple distribution is **inferred**; the configuration and `PetService.Incubation.Draw` demonstrate the same weighting. A tuple's type 1 is a pet, added to 5017 at level 1/star 1; a duplicate converts using `PetBaseConfig._kDecompose`, matching pet incubation collection. Type 2 is an item. `_iGuaranteedCnt` forces a roll from `_kGuaranteedBanner` at the threshold; an earlier hit in those groups resets the type-keyed pity counter. Group-hit reset, pity key `_iType`, and `mustCount` representation are **inferred** from the client `GetType` / `GetGuaranteedCnt` access in `UI_Sys_PetGachaWidgetCtrl.lua:630-690` and the DB fields. `_kRollNum=[1250710,10]` is awarded per draw as an **inferred** bonus interpretation. The 83410 result reports each raw draw, including duplicate `isBroken`, while 5011/5017 and inventory sync carry the durable state.

An owned draw commits ticket debit, item grant, pet roster, pool count and pity as one SQLite transaction through `CharacterService.ApplyAwardAsync`. The lottery blob stores `{Data, Day}` (protobuf bytes and civil day). Reconnect restores lifetime pity and counters; only daily-limit counts reset at day rollover. A one-second reconciliation updates `isOpen` and daily counters on clock or function changes, and a draw rechecks all gates under `ActivityGate` then `StateLock`. `33307 PET_LOTTERY` is handled by the existing pet refusal route; the positive Lua sender above uses 83410.

`LotteryActivityTests` exercises the game gate: closed-banner refusal with a valid reply object, owned 201 draws, shortage refusal, 5011 reconnect/day rollover, a same-connection role switch with independent durable counters, and twenty 200 draws yielding a guaranteed pet with a durable lifetime-cap refusal.
