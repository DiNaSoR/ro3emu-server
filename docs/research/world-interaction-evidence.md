# NPC gameplay interaction boundary

`WorldInteractionService` accepts 32700 status entry only through `SceneService`: the scene verifies the live scene-editor NPC, map, range, and `NPCConfig._iInteractID` before its prevalidation callback runs. `NPCInteractConfig._iStatusID` selects `GameplayStatusConfig._iStatusType`; 32702 carries that state, the authored interaction ID, and the NPC UID (`MG_Interact.proto:75-111`, `LC_GamePlayStatusMgr.lua:876-931`, `LC_Scene_Sync.lua:8751-8777`). Status 4 (sit) and 3 (vehicle) are implemented. Unknown status types and unimplemented predicates fail before the 32700 success echo. Error-code choices are inferred from `ErrorCodeConfig` meanings.

Vehicle entry requires `NPCConfig._iNPCSubType=103`, `_iSubTypeValue` matching `VehicleConfig`, and `_iStatusLocation` matching an authored `VehicleConfig._kSeats` entry and `VehicleSeatConfig`. Seat ownership is scoped to the world scene and NPC. 32708 is a zero-based seat move (`LC_VehicleServer.lua:143-167`); accepted moves send the seat's `_iChange3C` through 32704. 31074 accepts a finite face only from occupied driver seat zero (**inferred** restriction; `LC_PassengerComponent.lua:1680-1779` sends the seat-root yaw). 32703 accepts only an authored `GameplayStatusButtonConfig` Action button with `ActionConfig5004=QuitStatus`; client-provided skill payloads and 5001 do not grant arbitrary skills. Scene exit releases occupancy and sends idle state. The current generic `FunctionService.ConditionMet` does not implement GVG predicate 2202/camp 2200, so these fail closed here too.

The cannon branch is explicitly partial. `NPCInteractConfig` has exactly one status-2 row, 4900005. Nine `NPCConfig` templates (4900013-16 and 4900023-27) reference it, and `GVGCannonConfig` has nine corresponding rows with authored `_iSkillID`, `_kButtonActionIDs`, reload time and bullet limit. However, 4900005 requires `_iNPCCondition=4900001`: `LC_ConditionList` composes `CheckBuilder(2201,1)`, `CheckCamp(2200,1)` and inverse `CheckInteractState(12001,0)`. `LC_CommonCondition.lua:148-177,279-308` defines builder as the target unit's Owner UUID matching the local player and camp as equality of target/player camp. Those nine templates have camp 4; ordinary player AOI bases have camp 1, and `WorldNpc` has no owner field. No current GVG build lifecycle assigns a live cannon owner/camp, so a 32700 success for a static fixture cannon would fabricate permission. The service rejects status 2 before success. Consequently 32701 `UpdateCannonNotify{cannon_uid}` (the `LC_DunGeon_GVE.lua:141-179` UI/interaction enable transition) and 32705 `NpcSkillsCdNotify{npcUid,skillCds}` (registered in `LC_Scene_Sync.lua:404`) have no trustworthy cannon actor/CD producer. They are not sent as inert packets. 32703 `cannonUseSkill` from `LC_GVGFireCannon.lua:1908-2065` remains rejected until an owned cannon actor and skill/CD simulation exists; merely matching `_iSkillID` is insufficient to validate that producer's ammo, aim and cooldown.

A read-only semantic search covered `Cannon` (case-insensitive), `CheckBuilder`, and `CheckCamp` across **all** 517 config JSONs, 381 sceneeditor files, 172 nav files, 2 loc files, 13,488 files in each decompiled Lua tree (Logic and Config included), 2,277 decomp files and 147 proto files. Files with those patterns, in that order, were: config **12/0/0**, sceneeditor **0/0/0**, nav **0/0/0**, loc **1/0/0**, `re/lua-src` **82/2/3**, `re/clientB/lua-src` **82/2/3**, decomp **0/0/0**, proto **6/0/0**. The config matches include `GVGCannonConfig`, `NPCConfig`, `ActionConfig`, `BuffBehaviorConfig`, and localization. The two owner-predicate Lua files in each tree are `LC_CommonCondition.lua` and `LC_ConditionDefine.lua`; `LC_InteractCondition.lua` also names the camp predicate. A separate exact packet-symbol search found no 32701/32705 symbols in data or decomp and only network/consumer uses in Lua. These counts support the specific owner/camp boundary above, not a claim that the original server never ran a cannon encounter.

The placement search parsed every `kNpcList` in all 290 `data/sceneeditor/*_sceneeditor.json` files and found **zero** live NPC entries with `NpcId` 7100004 (sit), 4900301, 400140, 5300005, or 16300008 (vehicle). The 381-file sceneeditor directory also contains 89 `*_monsteridmap.json` files and two other files; the full protocol search covered those as well. A raw text hit for `7100004` in several minified sceneeditor files is not in `kNpcList`. Accordingly the service provides an authored-template-gated server state path and fixture test, but production status reachability for these templates is unqualified. This statement is limited to these IDs and this parsed placement search, not to all possible interactions. `NPCInteractConfig`, `GameplayStatusConfig`, `VehicleConfig`, and `VehicleSeatConfig` rows cited above are present in `data/config`.

For 31089, `re/lua-src/Logic/Asset/LC_DAL_Interact.lua:547-596` sends `ClientTeleportObject` with the local transform only when a unit has `m_bReverseMode`. The current server has no authoritative reverse-mode owner/lease or mutable scene-NPC position. Moving a target from that client request would permit arbitrary scene-object movement, so the handler rejects it with the existing parameter error. An exact-name `ClientTeleportObject` search over the roots listed in [world-effects-evidence.md](world-effects-evidence.md) found no data/decomp matches, Lua network registry names in both trees, and one proto declaration. The Lua sender was found by inspecting the asset interaction file directly, where the constant is spelled `CLIENT_TELEPORT_OBJECT`.

Validation: `tests/Ro3Emu.Tests/WorldInteractionTests.cs` covers sit and vehicle entry with temporary scene-editor fixtures (the fixture NPC must be on the map the role enters, here 10111). These are authored-fixture wire tests, not proof of production template reachability or live client rendering. See also [world-core-evidence.md](world-core-evidence.md).
